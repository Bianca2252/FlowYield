# FlowYield ROI Methodology

## 1. Purpose

This document defines how FlowYield estimates the operational and financial value generated by workflow automation.

The methodology must be:

- transparent;
- explainable;
- reproducible;
- testable;
- conservative;
- based on documented assumptions;
- suitable for portfolio demonstration;
- clearly separated from verified financial reporting.

FlowYield does not claim to produce audited financial results.

Its ROI outputs are estimates designed to support business analysis and process-improvement discussions.

---

## 2. Methodology Principles

### 2.1 Separate Measured and Estimated Data

Measured data comes from the application.

Examples:

- number of completed requests;
- average digital process duration;
- median digital process duration;
- number of workflow steps;
- SLA compliance;
- number of returned requests;
- number of rejected requests.

Estimated data is configured by the Process Manager.

Examples:

- manual processing time before automation;
- average hourly labor cost;
- manual interventions before automation;
- implementation cost.

The UI and documentation must clearly distinguish between measured and estimated values.

### 2.2 Make Every Formula Visible

Every KPI must have a documented formula.

Users should be able to understand:

- which inputs were used;
- which values are assumptions;
- which period is being analyzed;
- how the result was calculated;
- which limitations apply.

### 2.3 Avoid Guaranteed-Savings Language

FlowYield must use wording such as:

- estimated savings;
- projected annualized savings;
- estimated ROI;
- estimated payback period;
- modeled time reduction.

It must not use wording such as:

- guaranteed savings;
- verified financial benefit;
- audited ROI;
- certain cost reduction.

### 2.4 Use Conservative Defaults

Default assumptions should avoid exaggerating value.

Example assumptions:

- manual processing time: 45 minutes per request;
- digital processing time: measured or 15 minutes per request;
- average hourly employee cost: EUR 28;
- implementation cost: EUR 8,000.

These are demonstration values only.

---

## 3. Analysis Period

ROI calculations should use a defined reporting period.

Possible periods:

- current month;
- previous month;
- current quarter;
- previous quarter;
- current year;
- custom date range.

The MVP may initially support:

- current month;
- current year;
- all-time.

Every output must display the selected period.

---

## 4. Core Inputs

## 4.1 Number of Eligible Requests

Definition:

The number of requests included in the selected reporting period.

Recommended MVP rule:

```text
eligible_requests = completed requests
```

Completed requests include:

- APPROVED;
- REJECTED.

Cancelled drafts are excluded.

Active requests are excluded from finalized savings calculations.

---

## 4.2 Estimated Manual Processing Time per Request

Definition:

The estimated total employee time required to process one request before FlowYield.

This includes active manual work such as:

- preparing emails;
- checking spreadsheets;
- forwarding documents;
- following up with approvers;
- updating status trackers;
- recording decisions manually;
- producing reports.

It does not represent total calendar waiting time.

Unit:

```text
minutes per request
```

Source:

Configured assumption.

---

## 4.3 Estimated Digital Processing Time per Request

Definition:

The estimated or measured active employee time required to process one request using FlowYield.

Possible sources:

- configured estimate;
- measured interaction estimate;
- selected benchmark.

The MVP should prefer a configured estimate while also displaying measured calendar process duration separately.

Unit:

```text
minutes per request
```

Important distinction:

Digital processing time is active employee effort.

Process duration is elapsed calendar time from submission to completion.

These values must not be confused.

---

## 4.4 Average Hourly Employee Cost

Definition:

The estimated average fully loaded hourly labor cost for employees participating in the process.

It may conceptually include:

- salary;
- employer taxes;
- benefits;
- overhead allocation.

Unit:

```text
EUR per hour
```

The MVP does not calculate payroll data.

The value is a configurable business assumption.

---

## 4.5 Manual Interventions Before Automation

Definition:

The estimated average number of manual handoffs or administrative interventions required per request before FlowYield.

Examples:

- sending an email;
- forwarding an attachment;
- updating a spreadsheet;
- reminding an approver;
- copying a decision into another system.

Unit:

```text
interventions per request
```

---

## 4.6 Manual Interventions After Automation

Definition:

The estimated average number of manual administrative interventions remaining after FlowYield.

Approval decisions themselves are not automatically treated as eliminated manual work.

The model focuses on avoidable coordination and administration.

---

## 4.7 Estimated Implementation Cost

Definition:

The estimated total cost required to introduce FlowYield.

For the portfolio demo, this may include:

- design and development effort;
- configuration;
- training;
- deployment;
- maintenance setup.

Unit:

```text
EUR
```

The value is a configurable assumption.

---

## 5. Measured Operational Values

FlowYield can measure:

- total eligible requests;
- average digital process duration;
- median digital process duration;
- average duration by workflow step;
- SLA compliance rate;
- number of overdue steps;
- number of returned requests;
- number of rejected requests;
- average number of steps per request;
- volume by category;
- volume by department.

These values support ROI interpretation but do not all directly produce financial savings.

---

## 6. Core Formulas

## 6.1 Time Saved per Request

```text
time_saved_per_request_minutes
=
estimated_manual_minutes_per_request
-
estimated_digital_minutes_per_request
```

Example:

```text
45 - 15 = 30 minutes saved per request
```

If the result is negative, FlowYield must display the negative value or indicate that no time saving is estimated.

---

## 6.2 Total Hours Saved

```text
total_hours_saved
=
eligible_requests
*
time_saved_per_request_minutes
/
60
```

Example:

```text
120 * 30 / 60 = 60 hours saved
```

---

## 6.3 Processing-Time Reduction Percentage

```text
time_reduction_percentage
=
(
  estimated_manual_minutes_per_request
  -
  estimated_digital_minutes_per_request
)
/
estimated_manual_minutes_per_request
*
100
```

Example:

```text
(45 - 15) / 45 * 100 = 66.67%
```

If manual processing time is zero, the percentage is undefined.

---

## 6.4 Estimated Labor Cost Saved

```text
estimated_labor_cost_saved
=
total_hours_saved
*
average_hourly_cost
```

Example:

```text
60 * 28 = EUR 1,680
```

---

## 6.5 Estimated Saving per Request

```text
estimated_saving_per_request
=
estimated_labor_cost_saved
/
eligible_requests
```

Example:

```text
1,680 / 120 = EUR 14 per request
```

If eligible request count is zero, the result is not calculated.

---

## 6.6 Manual Interventions Eliminated

```text
interventions_eliminated
=
eligible_requests
*
(
  manual_interventions_before
  -
  manual_interventions_after
)
```

Example:

```text
120 * (6 - 2) = 480 interventions eliminated
```

This metric is operational, not automatically financial.

---

## 6.7 Monthly Estimated Savings

For a monthly reporting period:

```text
monthly_estimated_savings
=
estimated_labor_cost_saved_for_month
```

For grouped reporting, actual monthly data is preferred over dividing an arbitrary period.

---

## 6.8 Annualized Estimated Savings

```text
annualized_estimated_savings
=
average_monthly_savings
*
12
```

The result is a projection based on stable volume and assumptions.

---

## 6.9 Estimated ROI Percentage

```text
estimated_roi_percentage
=
(
  annualized_estimated_savings
  -
  estimated_implementation_cost
)
/
estimated_implementation_cost
*
100
```

Example:

```text
annualized savings = EUR 20,160
implementation cost = EUR 8,000

ROI = 152%
```

If implementation cost is zero, ROI percentage is undefined.

---

## 6.10 Estimated Payback Period

```text
payback_period_months
=
estimated_implementation_cost
/
average_monthly_savings
```

Example:

```text
8,000 / 1,680 = 4.76 months
```

If monthly savings are zero or negative, the UI should display:

```text
No positive payback under current assumptions
```

---

## 7. Avoiding Double Counting

MVP rule:

```text
Labor savings are calculated from time saved.
Interventions eliminated are displayed as a separate operational metric.
```

Interventions are not converted into additional cost savings in the initial methodology.

---

## 8. Calendar Duration Reduction

FlowYield also measures elapsed process duration.

```text
calendar_duration_reduction_percentage
=
(
  estimated_manual_calendar_duration
  -
  measured_digital_calendar_duration
)
/
estimated_manual_calendar_duration
*
100
```

This metric remains separate from active labor time savings.

---

## 9. SLA Value

SLA compliance does not directly produce a monetary saving in the MVP.

FlowYield displays:

- SLA compliance rate;
- overdue step count;
- average overdue duration;
- completed-on-time count;
- completed-late count.

The methodology does not invent a financial value for SLA violations.

---

## 10. Bottleneck Value

Bottleneck identification supports process improvement but is not automatically monetized.

FlowYield may show:

- slowest step;
- average step duration;
- median step duration;
- overdue frequency;
- volume handled by step type.

---

## 11. Approval, Rejection, and Return Rates

Approval rate:

```text
approval_rate
=
approved_requests
/
completed_requests
*
100
```

Rejection rate:

```text
rejection_rate
=
rejected_requests
/
completed_requests
*
100
```

Return-for-changes rate:

```text
return_for_changes_rate
=
requests_with_at_least_one_return
/
submitted_requests
*
100
```

These values require business interpretation and are not automatically positive or negative.

- Processed requests;
- Average digital duration;
- Median digital duration;
- SLA compliance;
- Overdue count;
- Step duration;
- Approval rate.

### Estimated

- Manual processing time;
- Hourly labor cost;

- Cost saved;

---

## 16. Versioning Assumptions

ROI assumptions should be versioned.

When assumptions change:

- previous values remain available;
- the new version becomes active;
- changes are audited;
- current calculations use the active assumption set.

Historical report snapshots may be added later.

---

## 17. Validation Rules

The ROI service must validate:

- manual minutes are non-negative;
- digital minutes are non-negative;
- hourly cost is non-negative;
- intervention counts are non-negative;
- implementation cost is non-negative;
- reporting period is valid;
- eligible request count is non-negative.

The service must safely handle:

- zero requests;
- zero manual time;
- zero implementation cost;
- zero monthly savings;
- negative time savings;
- incomplete assumptions.

---

## 18. Rounding and Currency Rules

Recommended presentation:

- hours: 1 or 2 decimal places;
- currency: 2 decimal places;
- percentages: 1 or 2 decimal places;
- payback period: 1 or 2 decimal places.

Internal monetary calculations should use decimal arithmetic.

The MVP uses EUR only.

---

## 19. Testing Requirements

Automated tests must cover:

### Time Savings

- positive;
- zero;
- negative;
- zero eligible requests.

### Time Reduction

- standard case;
- zero manual time;
- digital time greater than manual time.

### Cost Savings

- standard case;
- zero hourly cost;
- decimal currency values.

### ROI

- positive;
- zero;
- negative;
- zero implementation cost.

### Payback

- positive savings;
- zero savings;
- negative savings;
- zero implementation cost.

### Validation

- negative inputs;
- missing assumptions;
- unsupported currency.

---

## 21. Limitations

The methodology has the following limitations:

- manual process time is estimated;
- hourly cost is an average;
- saved time does not always become direct cash saving;
- process volume may change;
- implementation cost may exclude future maintenance;
- annualization assumes stable volume;
- quality improvements are not fully monetized;
- risk reduction is not monetized;
- SLA improvements are not monetized;
- avoided errors are not monetized;
- integration costs are excluded unless configured.

These limitations must be visible in the documentation and interface.

## 23. Definition of Done

The ROI feature is complete when:

- assumptions are versioned and validated;
- measured and estimated data are clearly separated;
- formulas match this document;
- currency calculations use decimal arithmetic;
- zero and negative cases are handled safely;
- the dashboard displays the assumption set;
- outputs are labeled as estimates;
- limitations are visible;
- automated tests cover every core formula;
- seed data produces a predictable demonstration result;
- the methodology is explained in the README.
